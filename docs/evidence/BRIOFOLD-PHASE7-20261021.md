# Phase 7 — Customers and identity linking

Scope: the Phase 7 section of BRIOFOLD-UNIFIED-IMPLEMENTATION-ROADMAP.bn.md. Implementation and automated acceptance are in progress; no production rollout or live identity-delivery proof is claimed yet.

The control CRM owns business/realm-scoped profiles, leads (new/contacted/qualified/proposal/won/lost), priority/reason, tags, assignees, preferences and timed team follow-ups. Every existing/new Inbox thread has its own source profile. An identical name, unverified email or phone never merges records. Financial records remain in their existing physical realms. Explicit source links validate ownership and environment through authorized Go reads. Existing financial customer screens remain at `/customers/financial`; a paginated import links their stable IDs without merging contact claims or overwriting CRM edits. Existing financial import/export APIs are preserved.

Verified merges require independently established matching identity and explicit confirmation; the oldest profile (creation time, UUID tie-break) is the deterministic canonical result. Customer-requested email confirmation uses a short-lived single-use hash-only capability delivered through the existing TLS SMTP transport. The browser receives it through a URL fragment and clears the fragment before confirmation. Signature-checked WhatsApp inbound account/sender identity can establish a scoped phone proof; historical contacts and typed numbers cannot. Email transport requires configured SMTP and CRM_PUBLIC_ORIGIN (HTTPS). Test SQL proof fixtures are not live email/provider evidence.

Dispute/unlink moves one source to a separate suppressed profile and revokes the old shared proofs. Merge retains the strictest opt-out/do-not-contact preferences; no new marketing consent is inferred. Follow-ups are internal reminders, not automatic outbound campaigns. Authoritative payment, invoice and order state is never inferred from CRM fields.

Owners/admins manage contacts, identity actions and exports. Editors can edit non-contact lead fields and reminders; viewers are read-only. Private contact/notes/proofs and contact searches are masked for non-owner/admin roles. Server-selected-business checks protect stale web tabs. All CRM tables use FORCE RLS with no raw runtime grants. The trusted Go API bridge uses the existing customers:write bearer scope; supplied contact details are always unverified. Commands are serialized per business, revision checked and idempotent; audit stores IDs/actions rather than personal values.

CRM export includes the profile, sources, proofs, reminders and complete CRM audit (bounded, explicit error over 10,000 events). Confirmed deletion erases CRM personal fields, proof/challenge data and reminder content across the merged cluster, retaining minimal tombstones/audit IDs to prevent source resurrection. Channel conversation retention and immutable financial retention remain separately governed and are stated in the UI.

Migration: `0140_briofold_customers.sql`, control only, additive. Requires 0139. Backfill creates separate profiles, never financial/customer payment records. Application rollback can leave additive CRM tables in place; do not run destructive down migrations. Deploy migration before the API because signed WhatsApp ingress now records the new identity proof.

Checks: local Go compile/unit suite, TypeScript, focused ESLint and syntax checks passed during development. The CI acceptance harness now applies 0140 and exercises actual PostgreSQL, signed HTTP and Next/browser journeys. Its final result must be recorded before sealing. No owner business/customer fixture or production mutation has been used for development.
