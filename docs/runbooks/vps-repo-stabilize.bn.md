# VPS আর রিপো এক অবস্থায় আনা (stabilize)

তারিখ: ২০২৬-১১-১৪। অবস্থা: শুরু হয়নি।
লক্ষ্য: প্রোডাকশনে যা চলছে আর GitHub-এর `main`-এ যা আছে, দুটো হুবহু এক হবে, আর সেটা প্রমাণ করা যাবে। এরপর টেস্ট, তারপর নতুন কাজ।

## ২. কাজের ধাপ

নিয়ম: এক ধাপ শেষ না হলে পরেরটা নয়। প্রতিটা ধাপের শেষে "শেষ হওয়ার প্রমাণ" দেখাতে হবে।

### ধাপ ক: থামানো (এখনই)

এই কাজ শেষ না হওয়া পর্যন্ত প্রোডাকশনে: নতুন ডিপ্লয় নয়, হাতে SQL নয়, মাইগ্রেশন টুল (`financial-migrate`) চালানো নয়।

### ধাপ খ: ইনভেন্টরি (শুধু পড়ে, কিছু বদলায় না)

VPS-এ:

```bash
cd /opt/briofold/rename-release/src && git fetch origin main && git show FETCH_HEAD:deploy/vps/inventory.sh > ~/inventory.sh
sudo bash ~/inventory.sh
```

এটা `/tmp/briofold-inventory-<তারিখ>.tar.gz` বানায়। ভেতরে: সার্ভার, কনটেইনার, ইমেজ, env-এর শুধু নাম (মান শুধু `_ENABLED` ফ্ল্যাগের), nginx, TLS, cron, তিন ডাটাবেসের খাতার সব সারি, প্রতিটা ফাংশনের ছাপ (md5), আর তিনটার গঠনের ডাম্প। কোনো গ্রাহকের ডেটা নেই।

ফাইলটা নিজের কম্পিউটারে এনে এজেন্টকে দিন। **রিপোতে তুলবেন না।**

শেষ হওয়ার প্রমাণ: স্ক্রিপ্টের শেষ লাইন `DONE: ...`, আর এই ডকের "জানা নেই" ঘরগুলো ভরা।

### ধাপ গ: তুলনা

1. রিপোর `main` থেকে খালি Postgres-এ তিনটা ডাটাবেস বানানো (CI যেভাবে বানায়)।
2. প্রোডাকশনের সাথে মেলানো: টেবিল, কলাম, ইনডেক্স, ট্রিগার, RLS policy, grant, extension, আর **প্রতিটা ফাংশনের ভেতরের কোড** (md5 দিয়ে)।
3. ফল একটা তালিকা: "প্রোডাকশনে আছে রিপোতে নেই", "রিপোতে আছে প্রোডাকশনে নেই", "দুই জায়গায় আলাদা"।

শেষ হওয়ার প্রমাণ: তিন ডাটাবেসের তালিকা, প্রতিটা সারির পাশে সিদ্ধান্ত (রিপোতে তোলা / প্রোডাকশন থেকে সরানো / ইচ্ছাকৃত, থাকবে)।

### ধাপ ঘ: রিপো ঠিক করা

- নতুন মাইগ্রেশন `0254_briofold_production_reconcile.sql`: ধাপ গ-এর "প্রোডাকশনে আছে রিপোতে নেই" অংশ হুবহু (কমপক্ষে `inbox_connection_named` আর ঠিকানা বদলের টুলসহ `briofold_ai_order_tool`)। প্রোডাকশনে চালালে কিছু বদলাবে না, এটাই শর্ত।
- `briofold_ai_financial_receipt_lookup` আর `dblink`: মালিকের সিদ্ধান্ত। প্রস্তাব: রিপোতে তোলা হবে না; কেউ ডাকে না প্রমাণ হলে আলাদা মাইগ্রেশনে প্রোডাকশন থেকে সরানো।
- CI-তে নতুন পরীক্ষা: রিপো থেকে বানানো ডাটাবেসের ফাংশনের ছাপ প্রোডাকশনের ছাপের তালিকার সাথে মিলতে হবে।

শেষ হওয়ার প্রমাণ: CI সবুজ, আর ধাপ গ আবার চালালে তালিকা খালি (ইচ্ছাকৃত সারি বাদে)।

### ধাপ ঙ: খাতা ঠিক করা

- পুরনো ছয়টা VPS-only সারি মোছা বা নাম বদলানো হবে না। এই ডকে "পুরনো সারি, এদের কাজ রিপোর ০২৫১ আর ০২৫৪-এ আছে" লিখে রাখা।
- রিপোর ০২৪৭ থেকে ০২৫৪-এর সারি খাতায় যোগ, রিপোর ফাইলের আসল sha256 দিয়ে। তিন ডাটাবেসেই, যার যেটা প্রযোজ্য (০২৪৮ শুধু দুই financial-এ)।
- এটা প্রোডাকশন ডাটাবেসে লেখা, তাই: আগে ব্যাকআপ, মালিকের অনুমতি, একটা স্ক্রিপ্ট দিয়ে, শুধু INSERT।
- নিয়ম: খাতায় ওঠা মাইগ্রেশন ফাইল আর কখনো বদলানো যাবে না (টুল checksum মেলায়)। বদল লাগলে নতুন নম্বরে নতুন ফাইল।

শেষ হওয়ার প্রমাণ: মাইগ্রেশন টুল "কিছু করার নেই" বলে শেষ হয়। আগে প্রোডাকশনের গঠনের কপিতে চালিয়ে দেখা, তারপর প্রোডাকশনে।

### ধাপ চ: একটাই ডিপ্লয় পথ

`deploy/vps/release.sh` (নতুন): যেকোনো কমিটের জন্য। ব্যাকআপ, খাতা দেখে বাকি মাইগ্রেশন চালানো আর খাতায় লেখা, ইমেজ বানানো, API চালু, health দেখা, সমস্যায় আগের ইমেজে ফেরা। `ai-payments-v2.sh` আর পুরনো `deploy.sh` এরপর অবসরে যাবে।

শেষ হওয়ার প্রমাণ: প্রোডাকশনের কপিতে স্ক্রিপ্ট চালানো, আর rollback পথটাও একবার চালিয়ে দেখা (এখন পর্যন্ত এটা কখনো পরীক্ষা হয়নি)।

### ধাপ ছ: মিল যাচাই আর চিহ্ন দেওয়া

- চলমান API ইমেজের কমিট = `main`-এর একটা কমিট।
- Vercel-এ চলমান ওয়েব = একই `main`।
- তিন ডাটাবেসের ফাংশনের ছাপ = রিপো থেকে বানানো ডাটাবেসের ছাপ।
- তখন git tag `prod-<তারিখ>`, আর `docs/AI-HANDOFF.md`-এ এক লাইন।

### ধাপ জ: টেস্ট

1. `main`-এ CI পুরো সবুজ।
2. ব্যাকআপ ফিরিয়ে আনার পরীক্ষা: সর্বশেষ ডাম্প আলাদা জায়গায় restore করে দেখা (VPS-এ নয়, RAM কম)।
3. প্রোডাকশনে ধোঁয়া-পরীক্ষা, মালিক নিজে: লগইন, ইনবক্সে মেসেজ, একটা টেস্ট অর্ডার (sandbox বা নিজের নম্বরে), পেমেন্ট যাচাই, Orders পেজে Paid ঠিক দেখায় কি না।
4. ২৪ ঘণ্টা API লগে নতুন এরর নেই।

এরপরই নতুন কাজ (`docs/plans/ai-production-ready.md` ধাপ ১ থেকে)।

## ৩. স্থায়ী নিয়ম

1. প্রোডাকশনে কোড বা SQL যায় শুধু GitHub-এর কমিট থেকে, শুধু ডিপ্লয় স্ক্রিপ্ট দিয়ে।
2. প্রতিটা মাইগ্রেশন খাতায় লেখা হয়। খাতায় ওঠা ফাইল বদলানো নিষেধ।
3. নতুন মাইগ্রেশনের নম্বর: রিপো আর প্রোডাকশনের খাতা, দুই জায়গার সর্বোচ্চ নম্বরের পরেরটা।
4. প্রতি ডিপ্লয়ের পর ছাপ মেলানো (ধাপ ছ) চলে।
5. গঠনের ডাম্প, env ফাইল, ব্যাকআপ কখনো রিপোতে নয়।

## ৪. জানা ঝুঁকি (মালিকের সিদ্ধান্তে আপাতত রাখা)

- **Postgres 5432 ইন্টারনেটে খোলা** (২০২৬-১১-১৪ যাচাই): ufw-এ সবার জন্য ALLOW, `pg_hba` লাইন ১২৯-এ যেকোনো ঠিকানা থেকে যেকোনো role ঢুকতে পারে (SSL আর scram পাসওয়ার্ড বাধ্যতামূলক)। Vercel-এর ওয়েব (`ekmivo_web_app`) এই পথেই ঢোকে, তাই পোর্ট বন্ধ করা যাবে না।
- ঝুঁকি: superuser `briofold_admin`-এর পাসওয়ার্ড ফাঁস হলে বাইরে থেকে পুরো ডাটাবেস।
- মালিকের সিদ্ধান্ত (২০২৬-১১-১৪): এখন কিছু বদলানো হবে না। **stabilize শেষ হলে মালিককে আবার মনে করাতে হবে।** তখনকার প্রস্তাব: `pg_hba`-তে শুধু বাইরে থেকে `briofold_admin` আটকানোর এক লাইন, ব্যাকআপ আর reload দিয়ে, আগে প্রোডাকশনের কপিতে পরীক্ষা করে।
